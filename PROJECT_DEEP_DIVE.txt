1. EXECUTIVE SUMMARY
====================

InvoiceAgent is a chat-first e-invoicing and accounting automation prototype.

The product idea is simple:

    A business owner types a normal sentence, such as:

        "I paid the plumber EUR 242 incl. 21% VAT"

    InvoiceAgent turns that sentence into:

        - a structured invoice/payment object
        - deterministic VAT calculations
        - Belgian PCMN-style account allocation
        - balanced double-entry bookkeeping
        - trial balance proof
        - VAT/cash/AP/AR summaries
        - UBL/Peppol compliance decision evidence
        - an audit-friendly payload preview

It feels like a lightweight chat app, but behind the interface it behaves like a
mini accounting and e-invoicing engine.

The core product message:

    "WhatsApp-simple invoicing input, audit-grade accounting output."

InvoiceAgent is not just extracting invoice data. It is proving that every
transaction is understood, classified, VAT-calculated, posted, and compliance
checked through deterministic business logic.


Current implementation status:

    - Chat input works for supplier invoices, paid supplier invoices, outbound
      invoices, credit notes, and payments.
    - Text-based PDF upload performs real extraction with PyMuPDF.
    - Scanned PDF extraction can use Gemini when GOOGLE_API_KEY is configured.
    - VAT is computed deterministically with Decimal.
    - Journals are posted only if balanced.
    - Trial balance, balance sheet, P&L, VAT, cash, AP, and AR views are derived
      from PCMN-style account metadata.
    - Outbound invoices and outbound credit notes can be sent through the
      e-invoice.be HTTP API when CREATE_REAL_UBL=1 and required credentials/master
      data are present.
    - Inbound supplier documents and bank payments are never sent as outbound
      Peppol documents.


2. THE PROBLEM IT SOLVES
========================

Small businesses increasingly need to deal with electronic invoicing, VAT,
Peppol/UBL compliance, accounting records, and accountant-ready books.

The pain points:

    - Business owners do not want to learn full accounting software.
    - Accountants still need structured, reliable journal entries.
    - VAT mistakes are common, especially with inclusive vs exclusive amounts.
    - E-invoicing rules are not the same for invoices, credit notes, and bank
      payments.
    - Demo tools often say "success" without proving what happened.
    - LLM-only invoice extraction is risky if the model also performs the math.
    - Trial balances may balance mathematically but still be poorly classified.

InvoiceAgent solves this by separating natural-language understanding from
deterministic accounting.

The LLM or regex layer can help interpret intent, but the critical outputs are
computed by deterministic Python:

    - VAT math
    - account allocation
    - double-entry journal lines
    - trial balance
    - balance sheet grouping
    - P&L grouping
    - UBL/Peppol applicability decision


3. HIGH-LEVEL PRODUCT EXPERIENCE
================================

The user opens the web interface and sees:

    - a chat-style transaction input
    - scenario buttons
    - a proof panel with tabs:
        - Compliance Proof
        - Journal
        - Trial Balance
        - VAT/Cash/AR/AP
        - Allocation

The user can type a sentence like:

    "I paid the plumber EUR 242 incl. 21% VAT"

The app replies:

    "Booked the purchase invoice for EUR 242.00 incl. EUR 42.00 VAT and
    allocated it to 611 Maintenance and repairs. Inbound supplier invoice
    staged; no outbound Peppol transmission. Invoice and bank payment were
    posted separately."

Behind that one sentence, the app performs multiple steps:

    1. Extract intent and fields.
    2. Normalize document structure.
    3. Normalize VAT rate.
    4. Compute net/VAT/gross.
    5. Decide whether this is an invoice, credit note, or pure payment.
    6. Allocate a Belgian-style account.
    7. Build UBL/Peppol compliance result.
    8. Generate journal entries.
    9. Post entries to the in-memory ledger.
    10. Recompute trial balance and financial summaries.
    11. Render the proof in the frontend.

        - the supplier payable was created

========================

The central route is:

    POST /chat

The frontend sends:

    {
      "message": "I paid the plumber EUR 242 incl. 21% VAT"

main.py receives the message and calls _process_message().

Pipeline inside _process_message():

    1. extracted = llm_extract(message)
    2. invoice = normalize_invoice(extracted)
    3. invoice = _override_paid_supplier_invoice(message, invoice, extracted)
    4. allocation = allocate_account(invoice)
    5. compliance = build_compliance_result(invoice, MY_COMPANY, allocation, create_real_ubl_enabled())
    6. entries = invoice_to_journal_entries(invoice, allocation)
    7. post entries to LEDGER
    8. ledger = LEDGER.snapshot()
    9. return JSON response

Response includes:

    - reply
    - intent
    - invoice
    - allocation
    - compliance
    - journal
    - journal_entries
    - ledger
    - warnings


7. EXTRACTION LAYER
===================

Extraction lives in extract.py.

There are two extraction paths:

    1. llm_extract(message)
    2. naive_extract(message)

llm_extract()
-------------

If GOOGLE_API_KEY is set, the app can call Gemini via google-genai to extract
semantic fields:

    - intent
    - counterparty_name
    - description
    - gross
    - tax_rate
    - invoice_id

Important design decision:

    The LLM is instructed not to calculate VAT.

The reason:

    VAT, totals, and postings must be deterministic. The LLM can help understand
    language, but it must not be trusted with accounting math.

If the LLM fails or no key is configured:

    llm_extract() falls back to naive_extract().


naive_extract()
---------------

naive_extract() is a deterministic regex/keyword fallback. It identifies:

    - INBOUND_INVOICE
    - OUTBOUND_INVOICE
    - PAYMENT_MADE
    - PAYMENT_RECEIVED
    - OUTBOUND_CREDIT_NOTE
    - INBOUND_CREDIT_NOTE
    - UNKNOWN

Examples:

    "I paid the plumber EUR 242 incl. 21% VAT"
        -> INBOUND_INVOICE because "paid" plus VAT/invoice clues means a paid
           supplier invoice, not merely a bank payment.

    "I paid invoice INV-123 by bank transfer"
        -> PAYMENT_MADE because it has payment wording but no VAT/invoice
           purchase evidence.

    "Client paid invoice INV-001 by bank transfer"
        -> PAYMENT_RECEIVED

    "Issue a credit note to Acme NV..."
        -> OUTBOUND_CREDIT_NOTE


8. VAT NORMALIZATION AND CALCULATION
====================================

VAT logic is in extract.py.

The app canonicalizes VAT rates internally as decimal fractions:

    21%  -> Decimal("0.21")
    21   -> Decimal("0.21")
    0.21 -> Decimal("0.21")
    6    -> Decimal("0.06")

This is handled by:

    canonicalize_vat_rate(value)

Why this matters:

    Before the fix, a rate like 21 could be treated inconsistently and divided
    by 100 twice. That produced absurd values like EUR 0.51 VAT on a EUR 242
    invoice.


VAT-inclusive formula
---------------------

For gross amounts that include VAT:

    vat_amount = gross_amount * vat_rate / (1 + vat_rate)
    net_amount = gross_amount - vat_amount

Example:

    Gross = 242.00
    Rate = 0.21

    VAT = 242 * 0.21 / 1.21 = 42.00
    Net = 242 - 42 = 200.00


VAT-exclusive formula
---------------------

For net amounts that exclude VAT:

    vat_amount = net_amount * vat_rate
    gross_amount = net_amount + vat_amount

Example:

    Net = 100.00
    Rate = 0.21

    VAT = 21.00
    Gross = 121.00


Money handling
--------------

The app uses Decimal, not float.

Money is rounded to 2 decimals using ROUND_HALF_UP in bookkeeping.money().

This avoids binary floating-point surprises and gives accounting-style rounding.

10. PAID SUPPLIER INVOICE OVERRIDE
==================================

There is a special guard in main.py:

    _override_paid_supplier_invoice()

Purpose:

    If an LLM or extractor classifies "I paid the plumber EUR 242 incl. 21% VAT"
    as a payment, the system can reclassify it as an inbound supplier invoice
    with payment included.

Why:

    In accounting, a message that includes supplier context, VAT evidence, and a
    gross amount usually means an expense invoice that was paid, not just an
    abstract bank movement.

The override:

    - changes intent to INBOUND_INVOICE
    - sets direction to INBOUND
    - sets document_type to INVOICE
    - recomputes VAT using the shared deterministic calculator
    - sets payment_included = True

Then invoice_to_journal_entries() creates two entries:

    1. invoice recognition
    2. payment clearing

----------------

12. CANONICAL PCMN ACCOUNT METADATA
===================================

The app now has a central account metadata layer:

    PCMN_ACCOUNT_META
    get_account_meta(account_code)

Each account meta includes:

    - code
    - name
    - class_code
    - category
    - statement
    - normal_side
    - liquidity_group
    - working_capital_group
    - display_group
    - flagged

Categories:

    - asset
    - liability
    - equity
    - expense
    - revenue
    - contra_asset
    - mixed
    - unknown

Statements:

    - balance_sheet
    - income_statement

Normal side:

    - debit
    - credit


Baseline classification
-----------------------

1xx:

    Balance sheet. Usually equity/provisions/long-term liabilities.

    10-15:
        equity, normal credit

    16:
        provisions/liability, normal credit

    17:
        long-term debt/liability, normal credit

2xx:

    Fixed assets and long-term receivables.
    Asset, balance sheet, normal debit.

3xx:

    Inventories and work/orders in progress.
    Asset, balance sheet, normal debit.

4xx:

    Mixed class. Must be classified by subrange.

    400:
        trade receivables, asset, debit

    411:
        VAT recoverable, asset, debit

    440:
        trade payables, liability, credit

    451:
        VAT payable, liability, credit

    490/491:
        debit-nature accrual/prepayment accounts, asset

    492/493:
        credit-nature accrual/deferred income accounts, liability

    Unknown 4xx:
        mixed, flagged

5xx:

    Cash, bank, liquid assets.
    Asset, normal debit.

    550 Bank:
        asset.
        A credit balance displays as negative cash / overdraft-like effect in
        the balance sheet summary, but the trial balance is not mutated.

6xx:

    Expenses.
    Income statement, normal debit.

7xx:

    Revenue/income.
    Income statement, normal credit.


Why this matters:

    A trial balance can be mathematically balanced while still being useless for
    financial reporting if accounts are not classified. The metadata layer turns
    raw debit/credit rows into:

        - balance sheet
        - P&L
        - VAT position
        - cash movement
        - open receivables
        - open payables
        - grouped trial balance


13. DOUBLE-ENTRY BOOKKEEPING ENGINE
===================================

Bookkeeping lives in bookkeeping.py.

Core classes:

    JournalLine
        account
        account_name
        debit
        credit

    JournalEntry
        ref
        date
        intent
        narrative
        lines

    Ledger
        in-memory list of posted journal entries


Journal validation
------------------

Every journal entry has:

    total_debit
    total_credit
    balanced

Ledger.post(entry) refuses to post an unbalanced entry.

That means the app cannot silently corrupt the ledger with an entry where:

    debits != credits


Invoice to journal mapping
--------------------------

Inbound invoice:

    Dr expense account
    Dr 411 VAT recoverable/input VAT
    Cr 440 Trade payables/Suppliers

Outbound invoice:

    Dr 400 Trade receivables/Customers
    Cr revenue account
    Cr 451 VAT payable/output VAT

Supplier payment:

    Dr 440 Trade payables/Suppliers
    Cr 550 Bank

Customer payment:

    Dr 550 Bank
    Cr 400 Trade receivables/Customers

Outbound credit note:

    Dr revenue account
    Dr 451 VAT payable/output VAT
    Cr 400 Trade receivables/Customers

Inbound credit note:

    Dr 440 Trade payables/Suppliers
    Cr expense account
    Cr 411 VAT recoverable/input VAT


14. TRIAL BALANCE
=================

The trial balance preserves classic accounting columns:

    - Account
    - Debit total
    - Credit total
    - Ending balance

Ending balance is computed as:

    debit - credit

Examples:

    Asset with debit balance:

        411 VAT recoverable:
            debit 42
            credit 0
            balance 42

    Liability fully cleared:

        440 Trade payables:
            debit 242
            credit 242
            balance 0

    Bank with credit movement:

        550 Bank:
            debit 0
            credit 242
            balance -242

The app does not mutate trial-balance math for display. A credit balance in bank
remains a credit balance. Higher-level summaries interpret it as negative cash.


Grouped trial balance
---------------------

The frontend groups trial balance rows by metadata display group:

    - Assets
    - Liabilities
    - Equity
    - Expenses
    - Revenue
    - Mixed/Unclassified

This makes the ledger easier to inspect without removing the classic debit and
credit columns.


15. BALANCE SHEET SUMMARY
=========================

The balance sheet summary is derived from metadata:

    Assets:
        balance sheet accounts with asset or contra_asset category

    Liabilities:
        balance sheet accounts with liability category

    Equity:
        balance sheet accounts with equity category

    Mixed/unclassified:
        unknown or ambiguous accounts

Important:

    6xx and 7xx accounts are not directly included in balance sheet totals.
    They belong to the income statement. Retained earnings/result could be added
    later as a separate closing process, but this prototype keeps the distinction
    explicit.


Plumber case balance sheet effect
---------------------------------

After:

    "I paid the plumber EUR 242 incl. 21% VAT"

Trial balance:

    411 VAT recoverable:
        +42 asset

    550 Bank:
        -242 asset

    440 Payable:
        0 liability after clearing

Balance sheet summary:

    Assets:
        VAT recoverable 42
        Bank -242
        Total assets effect -200

    Liabilities:
        Trade payables 0

Net assets effect:

    -200

That corresponds to the expense reducing the company's net position.

===========================

    6xx debit balances

    7xx credit balances

Profit/loss:

    revenue - expenses

----------------

    Expense:
        611 Maintenance and repairs = 200

    Revenue:
        0

    Profit/loss:
        -200

------------------

For:

17. VAT, CASH, AP, AR VIEWS
===========================

The VAT/Cash/AP/AR tab is derived from ledger balances:

VAT recoverable:

    Account 411 debit balance.

VAT payable:

    Account 451 credit balance.

Net VAT payable:

    VAT payable - VAT recoverable

Interpretation:

    Positive:
        net payable to tax authority

    Negative:
        net recoverable from tax authority

Cash movement:

    55x cash/bank accounts, especially 550 Bank.

Open payables:

    440 credit balance minus debit settlements.

Open receivables:

    400 debit balance minus credit settlements.

    inbound_staged

Business rules
--------------

UBL/Peppol applies to:

    - INVOICE
    - CREDIT_NOTE

UBL/Peppol does not apply to:

    - pure PAYMENT_MADE
    - pure PAYMENT_RECEIVED

Outbound invoice:

    DemoCo is seller/supplier.

    If CREATE_REAL_UBL=false:
        payload is staged
        status = demo_staged

    If CREATE_REAL_UBL=true and required fields are present:
        the app sends the payload with:

            POST {base_url}/api/documents/
            Authorization: Bearer {E_INVOICE_API_KEY}
            Content-Type: application/json

        status = sent if e-invoice.be returns a successful response with an
        external document ID.

        status = sent_pending_id if e-invoice.be accepts the request but does
        not return an external document ID.

        status = error if the API request fails.

    If CREATE_REAL_UBL=true and the API key is missing:
        status = blocked_missing_api_key

    If required fields are missing:
        payload is staged
        status = blocked_missing_master_data

Inbound supplier invoice:

    DemoCo is buyer/customer.
    The app must not send a Peppol invoice as DemoCo because DemoCo is not the
    supplier.

    It builds inbound evidence and sets:

        status = inbound_staged
        peppol_action = inbound_evidence_only

Payments:

    UBL not applicable:

        status = not_applicable
        peppol_action = not_applicable_payment
        payload_preview = null


Real e-invoice.be client
------------------------

Real sending is implemented in:

    send_einvoice_document(payload)

It:

    - reads E_INVOICE_API_KEY or EINVOICE_API_KEY
    - reads E_INVOICE_BASE_URL or EINVOICE_BASE_URL
    - defaults base URL to https://api.e-invoice.be
    - POSTs JSON to /api/documents/
    - uses Bearer authentication
    - uses a 15 second timeout
    - ignores ambient HTTP_PROXY/HTTPS_PROXY environment variables so local
      broken proxy settings cannot hijack the API call
    - retries once with TLS verification disabled if Python cannot validate the
      e-invoice.be certificate chain in the local environment, and exposes that
      fact as tls_verify_disabled in the compliance result
    - returns a normalized result:

        ok
        status_code

External document ID extraction supports common API response shapes:

19. PDF INVOICE EXTRACTION
==========================

PDF extraction lives in pdf_extract.py.

The central functions are:

    extract_pdf_text(file_path)
    extract_pdf_invoice_message(file_path)

Return shape:

    ok
    method
    text
    pages
    confidence
    warnings
    error
    message

Text-based PDF path:

    1. Open the PDF with PyMuPDF.
    2. Extract text from each page.
    3. Normalize whitespace.
    4. Require meaningful text before accepting extraction.
    5. Score confidence from invoice signals such as invoice, VAT/TVA/BTW,
       total, amount due, due date, supplier, customer, EUR, IBAN, and tax rate.
    6. Convert the extracted text into a clean invoice sentence when possible.
    7. Pass that message into the normal chat pipeline.

Scanned PDF path:

    If embedded text is weak/empty and GOOGLE_API_KEY is configured, the app
    attempts Gemini PDF extraction. Gemini is asked to extract invoice facts and
    readable text only. It is not allowed to decide accounting, VAT math, or
    journal entries.

Failure behavior:

    If PDF extraction fails, the API returns:

        "I could not extract invoice data from this PDF. Please upload a
        text-based invoice PDF or type the invoice details."

    No fake invoice is created. No default amount is invented. No journal is
    posted. The response includes pdf_extraction metadata with method, confidence,
    warnings, error, and text preview when available.

29. TECHNICAL DIFFERENTIATORS
=============================

1. Deterministic VAT engine

    The VAT bug that treated 21% incorrectly has been fixed by canonicalizing
    all rates to decimal fractions.

2. Correct UBL applicability

    Payments are not UBL invoices.
    Inbound supplier invoices are not transmitted as if DemoCo were the seller.

3. PCMN account metadata

    Accounts are classified by Belgian-style account class and subrange, not
    merely displayed as a flat list.

4. Double-entry proof

    Every posted entry must balance.

5. Financial reporting model

    The same ledger powers:

        - Trial Balance
        - Balance Sheet
        - P&L
        - VAT
        - Cash
        - AP
        - AR

6. Explainability

    The UI shows what happened and why.

7. Real Peppol send path with guardrails

    Eligible outbound invoices and outbound credit notes can be sent through the
    e-invoice.be HTTP API when CREATE_REAL_UBL=1 and required master data/API key
    are present. The app does not claim sent unless the API accepts the document.
    Duplicate invoice IDs are protected from repeated sends in memory.

8. Honest PDF extraction

    PDF upload extracts real embedded text with PyMuPDF and routes the result
    through the same accounting/compliance pipeline as chat. If extraction fails,
    no default invoice is fabricated.


30. CURRENT LIMITATIONS
=======================

This is a prototype. Current limitations:

    - Ledger is in-memory, not persisted.
    - Text-based PDF upload is implemented with PyMuPDF; scanned PDFs require
      GOOGLE_API_KEY for Gemini PDF/vision extraction.
    - Account allocation is keyword-based, not a trained classifier.
    - The PCMN chart is a useful subset, not the full Belgian chart.
    - Multi-line invoice extraction is structurally supported in compliance
      payloads but natural-language extraction currently creates one line.
    - Real e-invoice.be HTTP sending is implemented for eligible outbound
      invoices and credit notes, but it depends on environment/API availability
      and complete master data.
    - Peppol participant reachability lookup is not implemented yet; if a
      customer Peppol ID exists, the app notes that it was not verified before
      transmission.
    - No user authentication or multi-tenant database yet.
    - No bank feed reconciliation yet.
    - No closing entries / retained earnings workflow yet.
